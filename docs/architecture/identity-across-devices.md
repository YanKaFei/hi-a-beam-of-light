# 跨端身份决策

## 两个方案

**A · 设备独立身份，互不关联（推荐）**
每个设备生成自己的 RootIdentity；光种 = 一台设备上的一个匿名身份。
传光时通过邀请绑定关系，而不是合并身份。

- 优点：不需要在设备间传输种子；一台设备被攻破不影响另一台；隐私边界最简单。
- 代价："我的光"在多台设备上不一致，用户会问"为什么手机上是 1 个家族，电脑上是 2 个"。

**B · 每设备独立私钥 + 用户授权的设备关联**
主设备签发子身份证书，服务端记录"这两个身份属于同一用户"。

- 优点：跨端统一的光种体验。
- 代价：需要一个"关联"的信任根、需要用户显式授权流程、需要处理关联撤销；
  而且**一旦关联，匿名性被削弱**——两个设备的轨迹可以被合并分析。

## 结论（暂定，非永久）

**M1 采用 A。** 三条理由：

1. 第四阶段明确要求"不允许在微信小程序和 Android 之间直接传输长期身份私钥"，
   A 天然满足，B 必须额外设计才能满足。
2. B 的关联图谱本身就是敏感数据，和"匿名光种"的产品承诺冲突。
3. A 可以在不改变协议的前提下补 B（关联是加法），反过来不行。

## 尚未解决

- **恢复**：A 方案下设备丢失 = 光种丢失。需要设计"离线恢复凭据"（桌面端已有
  `export_recovery` 的实现可参考），M1 未做。
- **多设备用户预期**：需要在文案上明确"光种属于设备"。这不是技术问题，是产品表述问题。
