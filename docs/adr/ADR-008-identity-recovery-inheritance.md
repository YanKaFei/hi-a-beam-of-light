# ADR-008 · 光种恢复继承 + 跨平台验证接口

- **状态**：已采纳，核心已实现并有测试
- **决议来源**：D-02
- **日期**：2026-10-31
- **关联**：[ADR-009](ADR-009-e2-not-counted.md)、[ADR-010](ADR-010-node-identity.md)

## 背景

D-02 批准：「光种身份恢复继承机制，E2 仅本地显示」，
**同时**要求设计一个跨平台验证接口，使手机与小程序用户将来能够通过
**真实 AI 调用证明**获得等级，而不是永久停留在「寻光者」。

问题在于：手机与微信小程序**无法扫描本机 AI 应用**（产品文档 §9 已承认）。
若严格执行「只认 E3/E4」，这两端的知光称号会永久为 0 —— 一个看起来像 bug 的体验
（F0 缺口 G-19）。

## 决策：三条通路，按可信度排序

### 通路 1 · 光种恢复继承（当前可用）
同一个人在桌面端产生的已验证状态，通过恢复码恢复到移动端。
- 匿名 ID 由**根公钥**派生，恢复后不变（ADR-010）。
- 恢复的不是私钥副本，而是**签发新密钥的能力**，因此可轮换、可吊销。
- 移动端显示的等级**继承自该光种的已验证事实**，不新增证据。

### 通路 2 · 跨平台验证接口（F1 定义，F2/F3 落地）
服务端接受来自**受支持集成**的签名回执（E4）。形态：
1. 第三方 AI 客户端 / CLI 通过 `POST /v1/usage/attest` 提交带签名的调用回执；
2. `proof_method = signed_adapter_report` 或 `client_receipt_api`；
3. 该回执绑定 `anon_id`，因此移动端只要持有同一光种即可获得 E4。

这样移动端**不需要扫描任何东西**：它靠「别人替它证明了它调用过」。
这是唯一能在移动端成立的可信路径。

### 通路 3 · E2 自主确认（仅本地显示）
无任何验证条件时的兜底。见 ADR-009。

## 明确不做

- 不做「手机扫描手机」的伪验证（无法证明调用发生）。
- 不把 E2 通过任何路径升级为可信称号。
- 不为了移动端好看而放宽闸门（ADR-011）。

## 接口契约（F1 已定义，未实现服务端）

`UsageAttestRequest` 已固化于 `packages/protocol/schemas/usage_attest_request.schema.json`：
- `additionalProperties: false`，因此**无法**携带 token 数、提示词、密钥、数据库路径。
- `level` 只允许 `E3` / `E4` 进入可信统计（服务端 `CHECK` 二次兜底）。

## 后果

- 移动端与小程序有明确、诚实、可持续的取证路线，不依赖扫描本机。
- 但通路 2 依赖第三方客户端愿意签名——这是**外部依赖尚未满足**的部分，
  F1 状态记为 `PLANNED / 外部依赖`，不得宣称已实现。
