# ADR-009 · E2 自主确认不计入可信称号

- **状态**：已采纳，已在类型、存储、夹具三层实现并有测试
- **决议来源**：D-03（解决 F0 缺口 G-05）
- **日期**：2026-10-31

## 背景

产品文档对 E2 有三处互相拉扯的说法：
- §5.3：E2 标注「自主确认」，全球可信数不纳入；
- §6.1：知光称号按「已验证模型家族数」；
- §5.3 末段：称号与地图可以同时展示「自主确认」「已验证」两个数。

## 决策

**E2 永远不参与任何推导。** 它在三层各自被物理隔离：

1. **类型层**：`EvidenceLevel::E2.is_countable() == false`；
   `compute_light_state(verified, attested, …)` 的 `attested` 参数
   不进入 `level` 与 `knowledge_title` 的任何计算分支。
2. **存储层**：E3/E4 写 `countable_evidence`（`unique(family)`），
   E2 写**另一张表** `attested_family`。没有任何查询会 join 它们。
3. **契约层**：`usage_event.evidence_level` 有 `CHECK between 3 and 4`；
   共享夹具 `light_state.json` 包含「0 已验证 + 7 自主确认 → 仍是寻光者」的用例，
   Rust 与 TypeScript 两侧都必须给出相同答案。

## 界面呈现（F2 遵循）

- 主称号只反映 E3/E4。
- E2 以「自主确认 · N」单独呈现，视觉与文案上明确区别于主色。
- 命中 E3 后，E2 记录仍保留供用户回看自己的历史，但不再影响任何数字。

## 为什么不选择「E2 也计入，只是标注」

因为一旦计入，用户会看到「我从没真正用过，但我是拓界者」——
这正是产品文档 §1.5 明确反对的「把安装/领取当使用」。
称号一旦可以靠勾选获得，它就失去了全部意义。

## 后果

- 纯移动端用户的知光称号会低于其自我认知 → 由 ADR-008 的三条通路解决，
  而不是靠放宽 E2。
- 代价：需要在界面上多解释一句「自主确认不计入」。这是诚实的成本。
