# ADR-001 · 适配器证据边界必须是列级 allowlist

- **状态**：已采纳，已实现（`crates/adapter-sdk`），有 21 项测试
- **决议来源**：D-04
- **日期**：2026-10-31

## 背景

产品文档 §5.4、§12.3 禁止读取聊天正文、提示词、Cookie 与 API Key。
F0 审计发现这条禁令在实践中**无法按文件执行**：在真实客户端里，
`threads.model`（可用的 E3 证据）与 `threads.first_user_message`（用户原话）
在**同一张表**里。

因此只有两种可执行立场：

1. 整文件禁读 → 连带废掉唯一可行的 E3 通路，产品失去「本机可核验」这一层。
2. 整文件可读 → 直接违反隐私承诺。

两者都不可接受。

## 决策

边界落在**列**上，并且必须由**唯一的数据访问路径**执行。

四道机制，缺一不可：

1. **全局禁读清单**（`GLOBAL_DENY_COLUMNS`）——任何 manifest 都不能加入。
   违反者在 `validate()` 阶段就被拒绝，属于 CI 可捕获的失败，而不是运行时惊喜。
2. **逐适配器 allowlist**（`AdapterManifest.tables[].allow`）——未列出的列不可达。
3. **只生成 SQL**——`Connection` 是私有字段，查询由已校验的标识符拼装，
   `SELECT *` 在表达层面就不存在（`has_no_bare_star` 兜底断言）。
4. **只读句柄 + 审计**——连接只读（详见 ADR-012），每次查询（含被拒绝的）写入审计，
   审计只记录**列名**，永不记录值。

## 被放弃的替代方案

| 方案 | 为什么放弃 |
|---|---|
| 代码评审约定「不要读敏感列」 | 不可机械验证，一次疏忽就是不可挽回的事故 |
| 只允许整表读 | 被迫连 `first_user_message` 一起读，等于没有边界 |
| 运行时脱敏（读了再屏蔽） | 数据已经进入进程内存，脱敏为时已晚；日志、崩溃转储都可能泄漏 |
| 扫描后立即删除 | 仍是「先读」，与承诺冲突 |

## 后果

**好处**
- 「不读你的内容」变成可执行、可测试、可审计的约束。
- 新增适配器时，评审只需要看 manifest 就能判断数据面。
- 有一个反向压力：`adapter-codex` 的测试断言只可触及 3 表 7 列，
  任何扩张都必须改测试，从而强制一次评审对话。

**代价**
- 新适配器必须显式声明表与列，接入成本略高（这是刻意的摩擦）。
- 某些客户端若把元数据与内容混在同一列（例如把模型名塞进 JSON blob），
  该客户端就无法达到 E3，只能停在 E0/E1。这是正确的取舍：**宁可少一个适配器，
  也不越过边界。**

## 重新考虑的条件

- 出现一种客户端，其元数据必须从内容列解析才能获得 → 不得为它破例，
  应推动该客户端提供元数据，或放弃该适配器。
- SQLite 之外的数据源（如 HTTP API）→ 另行决策，但「列级声明 + 唯一路径 + 审计」
  三条原则应保留。
