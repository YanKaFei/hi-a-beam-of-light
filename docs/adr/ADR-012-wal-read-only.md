# ADR-012 · 活跃 WAL 数据库的只读打开策略

- **状态**：已采纳，已实现（`crates/adapter-sdk`），有测试
- **决议来源**：F1 实测发现（不是设计时预见的）
- **日期**：2026-10-31

## 背景：一次真实的失败

F1 首次把适配器指向真实客户端数据库时，扫描失败：

```
scan failed: query failed: unable to open database file
```

排查结论：**SQLite 无法以 `SQLITE_OPEN_READ_ONLY` 读取一个活跃的 WAL 数据库。**
读者需要 `-shm` 文件的写权限；只读句柄无法创建或获取它。
失败发生在**首次查询**而不是 open 调用——所以"open 成功"不能作为可读的证明。

## 决策：两级策略，并且如实上报用了哪一级

| 顺序 | 模式 | 说明 |
|---|---|---|
| 1 | `ReadOnly` | `SQLITE_OPEN_READ_ONLY` + `query_only` + **探测查询**。首选。 |
| 2 | `QueryOnly` | 仅在 1 失败时使用：OS 层可写打开 + `PRAGMA query_only = 1`，SQLite 在任何写语句**准备阶段**就拒绝。 |
| 3 | 失败 | 不搜索其他文件、不换路径、不扩大扫描范围。 |

关键细节：**必须做探测查询**（`select count(*) from sqlite_master`）才能确认可读，
因为 WAL 场景下 open 会成功而读取会失败。

`OpenMode` 会写入扫描报告，是可见事实而非隐藏实现细节。

## 为什么不用 `immutable=1`

`immutable=1` 能绕过 shm 问题，但它告知 SQLite「此文件不会变」。
对活跃数据库这是**谎报**：读取可能得到撕裂的页面或过时的数据。
用它来让测试变绿，就等于用一个错误的假设换取一个好看的数字。

## 本环境的一个额外事实（必须如实记录）

本次 F1 的沙箱**禁止写 `~/.codex/`**，因此第 2 级模式在此环境也失败。
把数据库复制到工作区后再以第 1 级打开则完全正常——这证明限制来自沙箱而不是 SQLite。
真实产品以用户本人身份运行、对自己的家目录有写权限时，第 1 级即可工作。

F1 的真实数据验证因此是在**工作区内的快照副本**上完成的
（`target/snapshot/`，验证后已删除）。该副本不会入库（`.gitignore` 排除 `*.sqlite`）。

## 后果

- 适配器在两种现实场景下都能工作，且用户数据永远不被写入。
- 第 2 级模式牺牲了「OS 层只读」这一层防御，因此用 `query_only` 补齐，
  并有测试断言写语句会被拒绝。
- **不引入 `immutable`**：宁可失败并提示，也不提供可能错误的数字。

## 重新考虑的条件

若某客户端的数据库长期被独占锁住导致两级都失败，
应当降级为「暂时无法校验」并如实展示，而不是绕过一致性。
