## 2. 缺口清单（文档未定义 / 自相矛盾 / 必须实测）

严重度：**S1** 会导致产品结论错误｜**S2** 会导致返工或无法验收｜**S3** 体验瑕疵

### G-01 · 「不读聊天正文」没有定义到可执行边界 —— S1

**问题**：文档禁止读聊天正文（§5.4、§12.3），但没说清「正文」的边界是谁来划定。
**实测证据**：本机 `~/.codex/state_5.sqlite` 的 `threads` 表**同时**含有：

- 可用元数据：`model`、`model_provider`、`created_at`、`updated_at`
- 禁读内容：`first_user_message`、`preview`、`title`

也就是说「整个文件禁读」会连带废掉唯一的 E3 通路；「整个文件可读」则直接违反隐私承诺。

**建议规则（需你确认）**：
1. 每个适配器提交 `AdapterManifest`，逐表声明 `allow` / `deny` 列。
2. `adapter-sdk` 是唯一查询入口，未声明列的访问在 debug 构建 panic，CI 直接红。
3. 适配器 PR 必须附「允许清单理由」，评审关注是否用最小列集达成目的。
4. `tokens_used` 列入 `allow` 但加 `purpose: diagnostic_only`，**禁止**用于评分、称号、上传。

### G-02 · 模型家族归一化规则缺失，会导致称号错判 —— S1

**实测**：真实数据 9 个 distinct 取值（8 个非空）→ 只有 1 个真实家族。

| 原始字符串 | 正确家族 | 如果 naive 计数 |
|---|---|---|
| `gpt-6-sol` | GPT | 算 1 个家族 |
| `gpt-5.6-sol` | GPT | 再算 1 个 |
| `gpt-5.6-terra` | GPT | 再算 1 个 |
| `gpt-6.1-sol` | GPT | 再算 1 个 |
| `gpt-6-astra` | GPT | 再算 1 个 |
| `chatgpt-web/gpt-6-sol` | GPT | 再算 1 个 |
| `chatgpt-web/gpt-5.6-sol` | GPT | 再算 1 个 |
| `codex-auto-review` | **非模型** | 再算 1 个 |
| `""` | 未知 | 再算 1 个 |

naive = 9 → 直接命中「拓界者」(≥7)；正确答案 = 1 → 「初明者」。
**这是用户一眼能看出的错误，且是最显眼的那颗光点的错误。**

**建议规则**：
1. 注册表是**数据文件**，不是 `if-else`；带 `version`，每次变更留 changelog。
2. 匹配按显式别名**从长到短**优先；不做「包含 gpt 就算 GPT」这类正则猜测。
3. 未命中 → `UNKNOWN`，**不计数、不猜、不折中**。
4. 每条别名必须写 `disposition`：`FAMILY` / `TASK_LABEL` / `UNKNOWN`。

### G-03 · 任务标签混入模型字段 —— S1

`codex-auto-review` 出现 203 次，是应用内部的自动评审任务标签。
若归入家族会凭空造出第十个"模型"。**建议**：`disposition: TASK_LABEL`，永不计数，但可在「已发现」里以中性文案呈现。

### G-04 · 客户端名被嵌进模型名 —— S2

`chatgpt-web/gpt-6-sol` 说明 `client` 与 `family` 在源头是混的。
**建议**：`client` 与 `model_family` 在数据模型里**必须分两列**（文档 §5.2 已要求），
解析规则：`<client>/<model>` 前缀视为 client，其余走别名表。

### G-05 · E2「自主确认」是否计入知光称号：文档自相矛盾 —— S1

- §5.3：E2 标注为「自主确认」，**全球可信数不纳入**。
- §6.1：知光称号按「**已验证**模型家族数」——按字面 E2 不计入。
- §5.3 末段又说「称号与地图可以同时展示『自主确认』『已验证』两个数」。

**三个说法互相拉扯**，且直接决定界面主称号。**建议**：
- 知光称号 = 仅 E3/E4 家族数（严格执行 §6.1 字面）。
- E2 单独呈现为「自主确认 · N」，视觉上明确区别于主色。
- 需要你拍板：**这是否可接受**（后果见 G-19）。

### G-06 · 「独立匿名节点」未定义，传光称号无法计算 —— S1

§6.2 称号基于「成功激活的独立匿名节点」，§6.2 末段又承认「不能保证节点绝对等同于不同自然人」。
但**"独立"的判定规则完全没写**：同一个人两台手机算 1 还是 2？同一设备重装算几次？

**建议**：
1. 计数单位定义为 **identity（光种公钥）**，不是设备。
2. 同一 identity 对同一 helper 的多次激活只计一次（唯一约束）。
3. 对多 identity 刷量，用**软性**手段：同 IP 段短时批量激活降权、新 identity 的激活需等待 24h 生效进入称号。**不做**设备指纹。
4. 对外文案统一说「激活节点」，不写「人」（文档已如此要求）。

### G-07 · 传光状态机缺超时、并发与重试语义 —— S2

§7.2 给了状态名，但没给：各状态超时多久、双方同时确认谁先、A 取消时 B 已确认怎么办、
重复点击是否幂等。**建议**：见 [05 状态机](05-state-machines.md) 的完整转移表（本方案已补全，待你审）。

### G-08 · 统计窗口与时区未定义 —— S2

「当前在线客户端」「今日新增点亮事件」「累计节点」都没有窗口与边界。
**建议**：全部 UTC 存储、按用户本地时区展示；显式字段 `window_start/window_end`；
在线 = 心跳窗口 90s 内的去重实例数。

### G-09 · 撤回承诺与聚合结构冲突 —— S1

A12 要求「删除服务端可关联事件」，§11.5 又允许「已不可逆的聚合结果」。
但文档没规定**原始事件与聚合结果如何物理分离**。
**建议**：`usage_event` / `light_edge` 为可删原始事实；`region_aggregate` 为只含计数、不含 identity 的汇总；
撤回时删除原始事实并**重算**受影响的聚合窗口，同时向用户说明历史快照不可逆。见 [03 文档](03-data-model.md)。

### G-10 · 恢复凭据是单点失窃风险 —— S2

§12.2 允许「通过恢复密钥主动迁移身份」，但没设计轮换/吊销。恢复短语一旦泄露，攻击者永久冒充。
**建议**：恢复短语仅用于**签发新密钥**（不是复制旧私钥），并支持 `key_epoch` 递增与旧 epoch 作废。

### G-11 · 反刷量阈值全缺失 —— S2

「燎原者」只需 100 个激活节点，无任何成本约束。§14.2 只说「降低重复设备刷量」，无机制。
**建议**：激活计入称号需 24h 冷却 + 同源聚类降权 + 单 identity 每日发起会话上限。阈值写进配置。

### G-12 · 里程碑命名冲突 —— S3

产品文档 §13.2 用 F0–F4 + GA；总控指令用 F0–F6。**本方案统一采用总控指令的 F0–F6**，并给出映射表（[06 文档](06-tasks-milestones.md)）。

### G-13 · NFC 的工程前提没写 —— S2

§7.4 说 iPhone 可读 NDEF，但真要做「触碰即打开接收页」必须满足：注册域名 + AASA 文件 +
App 关联域 entitlement + 已安装 App。缺任一项就退化为浏览器打开网页。
**建议**：V1.0 NFC 验收标准写为「触碰 → 打开**安全 HTTPS 接收页**」，不要求唤起 App；二维码始终并列。

### G-14 · 「微信小程序接入同一网络」缺可执行定义 —— S2

小程序无法扫描本机 AI 应用（§9 已承认），那么小程序用户能否拥有知光称号？文档没说。
**建议**：小程序定位为「接收/观看/传光」端；知光状态来自**已恢复的光种**（桌面端产生），
或仅显示 E2 自主确认。需你确认小程序是否允许 E2 计入主显（联动 G-05）。

### G-15 · `tokens_used` 的用法没有禁令 —— S2

实测该字段可读，且语义上极具诱惑（可用于"活跃度"）。文档 §1.5 禁止按消费额评价值，
但没禁止**读**这个字段。**建议**：显式写入协议禁令 + CI 断言该字段不出现在任何上传载荷中。

### G-16 · 品牌未定但代码需要标识 —— S3

§3.1 禁止固化品牌。**建议**：代码统一 `firstlight`，品牌串走 `brand.json`（见 [ADR-006](01-architecture.md)）。

### G-17 · 「每分钟 ≤2 次远方脉冲」是展示限频还是服务端限频 —— S3

**建议**：两侧都做。服务端按订阅者合并+限频；客户端再做一层展示节流（防重放/恢复历史时刷屏）。

### G-18 · 「亮度与颜色深浅分离计算」缺公式 —— S2

§4.3 要求深红内核仍有可辨识暖光外晕，但没给映射函数。
**建议**：`visual-system` 定义 `LightLevel → {coreColor, glowColor, glowRadius, luminance, breathPeriod}` 五元组，
并附无障碍对比度校验（深红在夜幕上仍需 ≥3:1 的轮廓识别度）。

### G-19 · 小程序/移动端永远到不了 E3，称号会"卡死在 0" —— S1

这是 G-05 的现实后果，单独列出：若严格执行「知光称号只认 E3/E4」，而小程序与移动端
无法扫描本机应用，则**整端用户的知光称号永久为「寻光者」**——一个看起来像 bug 的产品体验。

**三个可选解法（需你决策）**：
- **方案 A**：移动端/小程序通过「光种恢复」继承桌面端的已验证状态 → 称号正确，但要求用户先用桌面端。
- **方案 B**：E2 计入**本地展示**称号，但公域统计仍只认 E3/E4，界面明确标注「自主确认」。
- **方案 C**：移动端支持有限范围内的本地核验（如 iOS 上通过 Shortcuts/剪贴板授权读取）→ 成本高、体验碎。

**本方案倾向 A + B 组合**：有桌面端的走 A；纯移动端用户走 B 且视觉与文案严格区分。
