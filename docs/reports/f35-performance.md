# 性能与稳定性复测（F3.5 / A20）

设备：MacBook（Apple M2 Max）/ macOS 27.0.1 / 3024×1964 @2x
构建：debug + `--features test-control`
测量方式：应用自测（`getrusage` CPU 时间、`proc_pidinfo` 常驻内存）
原始数据：`target/f35-perf.json`

---

## 1. 结果

| 指标 | F2 基线 | **F3.5** | 目标 | 判定 |
|---|---|---|---|---|
| 空闲（动画中）CPU 均值 | 0.031% | **0.048%** | < 1% | PASS |
| 空闲（动画中）CPU 峰值 | 0.069% | **0.074%** | — | PASS |
| 空闲（安静模式）CPU | 0.004% | **0.033%** | — | PASS |
| 常驻内存 RSS | 112.7 MB | **113.2 MB** | 尽量 < 120 MB | PASS（余量 6.8 MB） |
| 扫描耗时（合成夹具） | 1 ms | **2 ms** | — | PASS |
| 30 s 稳定性 | — | **113.2 → 109.8 MB** | 无泄漏 | PASS |
| 退出后残留进程 | 无 | **无** | — | PASS |

---

## 2. 与 F2 的差异及原因

| 变化 | 幅度 | 原因 |
|---|---|---|
| 动画 CPU 0.031% → 0.048% | +0.017 个百分点 | 新增了传光仪式状态机（等待光环/光粒），空闲时仍需判断是否该绘制 |
| 安静模式 CPU 0.004% → 0.033% | +0.029 | 新增轮询与 SSE 线程在运行（未连接服务端时线程仍存在） |
| RSS +0.5 MB | 可忽略 | 身份与传光状态结构体 |

**结论：没有回退，仍在目标内。** 但安静模式的上升说明后台线程有成本，
F4 之前应让 SSE/轮询线程在未配置服务端时完全不启动。

---

## 3. 是否遵守"不得重新引入高频 JS 动画循环"

| 检查 | 结果 |
|---|---|
| 空闲时是否有 rAF 循环 | **否**。`schedule()` 只在仪式/过渡/光环活动时启动 |
| 呼吸与漂浮来源 | CSS 合成器动画（F2 结论，未改动） |
| 等待光环 | 仅在有进行中的邀请时绘制，且受 30 fps 上限 |
| 光粒迁移 | 仅 2.6 s，随后停止 |
| 仪式结束后 | 循环自行停止（`busy` 为假） |

空闲 CPU 0.048% 与 F2 的 0.031% 同量级，说明没有引入常驻循环。

---

## 4. 窗口交互与稳定性

| 项 | 结果 |
|---|---|
| 面板打开/关闭 | 正常；关闭后不残留线程 |
| 双击/重复点击发起邀请 | 由 `Idempotency-Key` 与服务端每日上限约束（F3 已测） |
| 服务端不可达 | 光点照常运行（A16） |
| Ctrl-C / 退出 | 无残留进程（`pgrep` 空） |
| 30 s 内内存 | 略降（-3.4 MB），无增长趋势 |

**未测**：长时间（≥8 小时）挂机。F2 结论不变：45 秒/30 秒窗口能排除明显泄漏，
排除不了缓慢泄漏。建议 F6 前补一次。

---

## 5. 复现

```bash
cargo build -p firstlight-desktop --features test-control
python3 apps/desktop/tests/f2_perf.py \
  --idle-seconds 8 --stability-seconds 30 \
  --out target/f35-perf.json
```

脚本会自行启动/停止应用；需要 `--features test-control` 的构建，
否则控制通道不存在（这正是 A18 要验证的）。
