# 性能与稳定性报告（F2 第七阶段）

设备：MacBook（Apple M2 Max）/ macOS 27.0.1 / 3024×1964 @2x
构建：debug（未开 release 优化，真实产品会更低）
测量方式：**应用自测**（`getrusage` 取 CPU 时间、`proc_pidinfo` 取常驻内存），
因为本环境的 `ps` / `top` 被沙箱禁用。

原始数据：`target/f2-perf-valid.json`（优化后）、`target/f2-perf.json`（首版基线）

---

## 1. 先测基线，再定预算

产品文档 §14.3 给的目标是「空闲 CPU 平均 < 1%，常驻内存尽量 < 120 MB」。
按授权书要求，先测真实基线，再决定做什么。

### 1.1 首版基线（每帧重建径向渐变 + 每帧绘制）

| 指标 | 值 |
|---|---|
| 空闲（动画中）CPU 均值 | **4.48%** |
| 空闲（动画中）CPU 峰值 | 4.79% |
| 空闲（安静模式）CPU | 0.005% |
| 常驻内存 | 113.2 MB |

**结论：超出目标 4.5 倍，必须优化。** 而且这不是"fluff"——一个 9 秒周期的呼吸
用了 4.5% CPU，长期运行会明显影响笔记本续航。

---

## 2. 做了两次优化，第一次不够

### 尝试 1：缓存精灵 + 30fps 上限
把每帧重建两个径向渐变改成"预烘焙到离屏画布"。

| 指标 | 优化前 | 尝试 1 |
|---|---|---|
| CPU 均值 | 4.48% | 3.65% |

只降了 18%。说明瓶颈不在渐变构建，而在**每帧的 JS 绘制与合成**本身。

### 尝试 2：把呼吸与漂浮交给合成器（关键）
洞察：呼吸只是整体透明度变化，漂浮只是整体位移——这两件事**不需要 JS 逐帧计算**。

- 内核与光晕一次性烘焙进精灵；
- 呼吸 → `@keyframes` 改 `opacity`；
- 漂浮 → `@keyframes` 改 `transform: translateY()`；
- JS 循环只在**等级过渡**与**光环事件**期间运行，其余时间为零帧。

| 指标 | 首版 | 最终 | 相对首版 |
|---|---|---|---|
| 空闲（动画中）CPU 均值 | 4.48% | **0.031%** | **-99.3%** |
| 空闲（动画中）CPU 峰值 | 4.79% | 0.069% | -98.6% |
| 空闲（安静模式）CPU | 0.005% | 0.004% | — |
| 常驻内存 | 113.2 MB | 112.7 MB | — |

## 4. 测量口径（必须说清，否则数字会被误读）

| 项 | 说明 |
|---|---|
| CPU 是什么 | 应用进程自身的 `ru_utime + ru_stime` 增量 / 窗口时长。**不含 WindowServer 的合成开销** |
| 为什么不含 | 任何桌面应用都这样报；把所有合成都算进来会把 Chrome、Finder 一起算进去。要看系统总开销需另测 |
| 内存是什么 | `proc_pidinfo(PROC_PIDTASKINFO).pti_resident_size`，即常驻集 |
| 为什么内存下不去 | 112 MB 里绝大部分是 WebKit 进程与共享库；F2 没有自建渲染层。若需进一步压低，F3+ 可评估用原生绘制替换 WebView |
| 扫描用时 | 基于**合成夹具**（11 个会话）。真实客户端 347 个会话时会更大，但仍是毫秒级 |

### 关于 `< 120 MB` 的诚实评价
112.7 MB 达标，但**余量只有 7 MB**。这不是一个好的余量。
建议在 F3 记录为技术债：若后续加入光场可视化或更多适配器，很可能突破。
可选路径：把光点渲染移出 WebView、或拆分独立轻进程。

---

## 5. 稳定性

| 项 | 结果 |
|---|---|
| 连续运行 45 s（含 5 次扫描） | 进程存活，RSS 113.4 → 113.4 MB，**零增长** |
| 退出后残留进程 | 无（`pgrep` 空） |
| 退出路径 | 通过控制通道 `quit` → `app.exit(0)`，干净 |
| 扫描失败后仍在运行 | 是（端到端 H/I） |
| 服务离线 / 无客户端数据 | 不崩溃（端到端 H） |

**未做**：数小时的长时间运行测试。45 秒能排除明显泄漏，但排除不了缓慢泄漏。
建议 F6 做一次 ≥8 小时的挂机测试。

---

## 6. 数据库读取失败时的行为

| 情况 | 行为 | 证据 |
|---|---|---|
| 扫描未授权 | 状态 `not_authorized`，不读任何数据，光点保持原状 | 端到端 I |
| 找不到客户端 | 状态 `client_not_found`，说明原因，光点保持原状 | 端到端 H |
| 读取失败（含沙箱拒绝） | 状态 `failed`，明确说明"不会扩大范围/不提权" | 真实沙箱环境复现 |
| 本地库损坏 | `light-store` 返回 `FutureSchema`/错误，不破坏数据 | `future_schema_is_refused_rather_than_corrupted` |

## 7. 复现命令

```bash
# 性能基线
python3 apps/desktop/tests/f2_perf.py \
  --binary target/debug/firstlight-desktop \
  --idle-seconds 12 --stability-seconds 45 \
  --out target/f2-perf-valid.json
```

单次运行约 70 秒。脚本会自己启动/停止应用，不需要手动准备。

## 8. 结论

| 结论 | 依据 |
|---|---|
| 空闲 CPU 达标且余量充足 | 0.031% vs 目标 1% |
| 空闲内存在目标内但余量偏小 | 112.7 / 120 MB，记为技术债 |
| 无明显内存泄漏（45s 窗口内） | 零增长 |
| 退出干净，无残留 | `pgrep` 空 |
| 优化是真实生效的，不是测量误差 | 优化前后同一脚本、同一机器；并用 `probe` 确认动画确实在运行 |

最后一条值得强调：第一版优化后曾测到 0.033%，但当时页面脚本因
`applyCssMotion` 未定义而抛异常、动画**根本没跑**——那个数字是假的。
修复后重测仍为 0.031%，并以 `probe` 的 `loopRunning` / `coreName` 变化
证明动画确实在运行，才把这个数字写进报告。
